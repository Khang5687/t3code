# Bind one socket per selected listen interface instead of `0.0.0.0` plus peer filtering

Upstream's exposure model is two-valued: loopback, or `0.0.0.0` with Tailscale integration. The fork models exposure as a set of listen-interface kinds — `loopback` (always), `tailnet`, `lan`, plus an optional explicit IP list for a `custom` preset — carried through the contract and CLI as `listenInterfaces`. The server resolves kinds to concrete addresses at launch (via `@t3tools/tailscale`'s `isTailscaleIpv4Address`, no `tailscale` CLI dependency) and opens one listen socket per resolved address; if the tailnet is absent at launch it binds loopback only and warns. Any non-loopback interface implies the `remote-reachable` auth policy; advertised endpoints are derived from the selection; changing exposure still relaunches the backend. An optional `allowedPeers` list narrows who may connect to the interfaces that are bound: entries are IPv4 addresses or CIDRs, they ride the selection as `allow:` entries in the `--host` spelling (so `--allow-peer`, `T3CODE_ALLOWED_PEERS`, and the desktop's bootstrap envelope all reach the resolver through the one channel), and the server enforces them on the accepted socket before the HTTP parser runs. The effective list is the request itself, plus a host route per explicit bind address, plus `127.0.0.0/8` so a machine cannot lock itself out; a selected kind's default range is never folded back in, because `--host lan --allow-peer 192.168.1.5` widened by `lan` would still admit all of 10/8, 172.16/12 and 192.168/16 and restrict nothing. Absent means no restriction beyond the bind. The allowlist is matched as IPv4, so an IPv6 bind other than `::1` refuses every peer that arrives on it; the resolver warns when a selection asks for both. Proxy headers such as `X-Forwarded-For` are deliberately ignored: behind a proxy every peer is the proxy, and a client-settable header would make the allowlist advisory.

True per-interface binding was chosen because the kernel enforces it — a filtered `0.0.0.0` listener is still a listener. Kinds were chosen over raw IPs (DHCP changes them) and over OS interface names (`en0`, `tailscale0`; OS-specific), and server-side resolution keeps one implementation for desktop, CLI `--host`, and the WSL backend. Escape hatch: only if `HttpServerLive` cannot be instantiated once per address do we fall back to `0.0.0.0` with a `socket.localAddress` check.

Inside WSL the selection means what WSL's interfaces say, not what Windows' do. The desktop sends the same selection into the distro and the Linux server resolves it there, so under WSL2's default NAT networking the distro sees only loopback and its virtual NIC: `lan` binds an address on the WSL-vEthernet network rather than the real LAN, and `tailnet` resolves to nothing unless Tailscale runs inside the distro. Making that selection reach the real LAN needs `netsh interface portproxy` on the Windows side, or WSL2 mirrored networking, where the distro shares the host's interfaces. We record the limitation instead of proxying around it: the desktop advertises the distro IP only for a selection carrying `lan`, and anything narrower reaches the backend through WSL2 localhost forwarding.

The bind stays as it is; what changed is that the resolver now says so. `detectWslNetworking` (`packages/tailscale/src/listenInterfaces.ts`) reads the distro's networking mode from the interfaces it ended up with, because the mode is set on the Windows side in `%UserProfile%\.wslconfig` where the distro cannot read it: a `loopback0` interface means mirrored, external addresses confined to 172.16.0.0/12 mean NAT, anything else is unknown and warns like NAT. Under NAT the `lan` warning names the bound address and the two ways out, and a missing tailnet points at the distro rather than the machine. Both ride the existing `warnings` list, so they reach the CLI startup output, the persisted runtime state, and the desktop exposure panel with no new channel. The peer allowlist does not follow: since it narrows to exactly what was asked for, a WSL user who sets one has to list the Windows-host gateway on 172.16.0.0/12 themselves, or Windows is locked out of the distro's server.

Taking that forwarding dependency back is a deliberate trade. Upstream bound `0.0.0.0` inside the distro precisely to avoid it, after readiness probes and renderer fetches failed with "Failed to fetch" on hosts where the forwarder misbehaves. We prefer the honest bind: a wildcard is a listener the kernel really opens, so it makes "Limited to this machine" false for anyone running Tailscale inside the distro, and mirrored networking fixes forwarding properly for the hosts that need it. The bind itself is unverified on a real WSL machine; the mode detection is covered by fixture tests only. If the failure comes back, the answer is to fall back to the distro NIC when the loopback readiness probe fails, not to restore the wildcard.

One gap is deliberate. A Windows desktop resolves exposure against Windows' interfaces, so its own panel reads `not-wsl` and the warnings its WSL backend raises stay in that backend's log and runtime state. Carrying them to the panel needs a structured channel from the child server, which is a feature, not a warning. A desktop running inside the distro under WSLg, and a plain `t3 serve` in a distro shell, both get the warnings today.
